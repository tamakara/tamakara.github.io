## 网络分层

### 为什么需要分层

计算机网络需要同时解决很多不同的问题：

```text
数据如何传输？
↓
局域网内如何找到设备？
↓
跨网络如何找到目标主机？
↓
数据经过哪些网络？
↓
如何找到目标主机上的具体进程？
↓
如何保证数据可靠到达？
↓
应用程序如何理解这些数据？
```

这些问题属于不同的职责，因此网络采用分层设计。

本文使用常见的 TCP/IP 四层模型：

| 层     | 核心问题           | 典型协议 / 技术               |
| ----- | -------------- | ----------------------- |
| 应用层   | 应用程序交换什么数据     | HTTP、HTTPS、DNS、DHCP、SSH |
| 传输层   | 哪个进程通信，以及如何传输  | TCP、UDP、Port            |
| 网际层   | 数据送到哪台主机、如何跨网络 | IPv4、IPv6、ICMP、Routing  |
| 网络接口层 | 数据如何在当前链路传输    | Ethernet、Wi-Fi、MAC、ARP  |

RFC 1122 对 Internet 协议体系中的 Host-to-Host Communication 进行了系统描述。([RFC 1122](https://www.rfc-editor.org/rfc/rfc1122))

### TCP/IP 四层与 OSI 七层

OSI 模型：

```text
7  应用层
6  表示层
5  会话层
4  传输层
3  网络层
2  数据链路层
1  物理层
```

TCP/IP 四层模型通常可以对应为：

```text
TCP/IP                OSI

应用层                应用层
                      表示层
                      会话层

传输层                传输层

网际层                网络层

网络接口层            数据链路层
                      物理层
```

两种模型并不是严格的一一对应关系。

更重要的是理解：

```text
应用层
→ 应用之间交换什么

传输层
→ 进程之间如何通信

网际层
→ 主机之间如何通信

网络接口层
→ 当前链路如何传输
```

### 数据在各层中的名称

同一份数据经过不同协议层后，通常会有不同的名称：

| 层        | 数据单元                 |
| -------- | -------------------- |
| 应用层      | Data / Message       |
| TCP      | Segment              |
| UDP      | Datagram             |
| IP       | Packet / IP Datagram |
| Ethernet | Frame                |

典型封装过程：

```text
应用数据
    ↓
TCP Segment
    ↓
IP Packet
    ↓
Ethernet Frame
```

接收端则反向处理：

```text
Ethernet Frame
    ↓
IP Packet
    ↓
TCP Segment
    ↓
应用数据
```

这分别称为：

```text
封装 Encapsulation
解封装 Decapsulation
```

网络数据最终必须转换成可以在物理介质上传播的信号。

常见介质：

```text
双绞线
光纤
无线电波
```

例如：

```text
主机
 ↓
双绞线
 ↓
交换机
```

或者：

```text
无线终端
 ↓
无线电波
 ↓
AP
```

因此从最底层看：

```text
数字数据
↓
编码
↓
物理信号
↓
网络介质
```

不同物理介质具有不同的：

```text
带宽
传输距离
抗干扰能力
成本
```

## Ethernet

Ethernet 是最常见的局域网技术之一。

它以：

```text
Frame
→ 帧
```

作为基本传输单位。

一个简化的 Ethernet Frame：

```text
┌────────────┬────────────┬────────────┬──────────────┐
│ Destination│    Source  │    Type    │     Data     │
│    MAC     │     MAC    │            │              │
└────────────┴────────────┴────────────┴──────────────┘
```

其中：

```text
Destination MAC
→ 当前这一跳的目的设备

Source MAC
→ 当前这一跳的发送设备
```

注意这里的关键词：

> **当前这一跳。**

MAC 地址主要用于当前链路中的二层通信，而不是整个 Internet 的端到端寻址。

---

## MAC 地址

MAC 地址用于标识网络接口的链路层地址。

例如：

```text
00:1A:2B:3C:4D:5E
```

在 Ethernet 网络中，交换机通常维护：

```text
MAC 地址
    ↓
交换机端口
```

例如：

```text
MAC A → Port 1
MAC B → Port 2
MAC C → Port 3
```

当交换机收到：

```text
Destination MAC = MAC B
```

就可以将帧转发到：

```text
Port 2
```

因此可以简单理解：

```text
MAC
→ 当前二层网络中的地址

Switch
→ 根据 MAC 进行二层转发
```

---

## 交换机

交换机主要负责局域网内部的二层转发。

典型结构：

```text
主机 A
  │
  ↓
交换机
  ├── 主机 B
  ├── 主机 C
  └── 主机 D
```

交换机关注的是：

```text
MAC 地址
+
端口
```

而不是 Internet 中的完整路由路径。

因此：

```text
交换机
→ 二层

路由器
→ 三层
```

## ARP

IPv4 局域网中，主机经常同时需要：

```text
目标 IP
目标 MAC
```

例如：

```text
目标 IP
192.168.1.20
```

但 Ethernet 帧需要：

```text
目标 MAC
AA:BB:CC:DD:EE:FF
```

因此需要：

```text
IP
↓
MAC
```

的地址解析机制。

ARP（Address Resolution Protocol）就是用于这一目的。

RFC 826 定义了 ARP 的基本机制。([RFC 826](https://www.rfc-editor.org/rfc/rfc826))

### ARP 工作过程

假设：

```text
主机 A
IP = 192.168.1.10

主机 B
IP = 192.168.1.20
```

A 不知道 B 的 MAC。

于是发送 ARP Request：

```text
谁拥有：

192.168.1.20？

请告诉：

192.168.1.10
```

B 回复：

```text
192.168.1.20
↓
AA:BB:CC:DD:EE:FF
```

于是 A 建立：

```text
192.168.1.20
        ↓
AA:BB:CC:DD:EE:FF
```

的映射。

---

## ARP 与路由的关系

ARP 一个非常容易混淆的地方是：

> 跨网段通信时，主机通常不会 ARP 获取最终服务器的 MAC。

例如：

```text
本机
192.168.1.10/24

目标
8.8.8.8
```

目标不属于：

```text
192.168.1.0/24
```

因此本机不能直接通过当前二层网络把帧交给：

```text
8.8.8.8
```

而是先交给：

```text
默认网关
192.168.1.1
```

此时 ARP 查询的是：

```text
192.168.1.1
↓
网关 MAC
```

因此：

```text
同网段
→ ARP 找目标主机 MAC

跨网段
→ ARP 找下一跳 MAC
```

这是理解：

```text
ARP
+
IP
+
Route
```

之间关系的关键。

## VLAN

VLAN（Virtual LAN）用于在二层网络中进行逻辑隔离。

例如：

```text
VLAN 10
→ 办公网

VLAN 20
→ 服务器网

VLAN 30
→ 访客网
```

可以理解为：

```text
             物理交换网络
            /      |      \
           /       |       \
       VLAN 10  VLAN 20  VLAN 30
```

不同 VLAN 通常属于不同的二层广播域。

### Access 与 Trunk

交换网络中常见：

```text
Access
Trunk
```

可以简单理解：

| 类型     | 典型用途             |
| ------ | ---------------- |
| Access | 连接终端，通常承载一个 VLAN |
| Trunk  | 在网络设备之间传输多个 VLAN |

IEEE 802.1Q 定义了 VLAN 的相关机制。

## IPv4

IPv4 地址长度：

```text
32 bit
```

例如：

```text
192.168.1.100
```

二进制表示：

```text
11000000.10101000.00000001.01100100
```

IPv4 地址通常由：

```text
网络前缀
+
主机部分
```

组成。

---

## IPv6

IPv6 地址长度：

```text
128 bit
```

例如：

```text
2001:db8::1
```

相比 IPv4：

```text
IPv4
→ 32 bit

IPv6
→ 128 bit
```

IPv6 的核心规范是 RFC 8200。([RFC 8200](https://www.rfc-editor.org/rfc/rfc8200))

---

## IP 地址、MAC 地址、端口

这三个概念应该明确区分：

| 标识   | 所在层次  | 主要作用         | 示例              |
| ---- | ----- | ------------ | --------------- |
| MAC  | 网络接口层 | 当前链路定位设备     | `00:1A:2B:...`  |
| IP   | 网际层   | 跨网络定位主机 / 接口 | `192.168.1.100` |
| Port | 传输层   | 定位传输层端点      | `443`           |

可以记成：

```text
MAC
→ 当前这一跳找谁

IP
→ 网络中找哪台主机

Port
→ 主机上的哪个网络端点
```

## CIDR

CIDR（Classless Inter-Domain Routing）使用：

```text
/数字
```

表示网络前缀长度。

例如：

```text
192.168.1.0/24
```

表示：

```text
前 24 bit
→ 网络前缀

剩余 8 bit
→ 主机部分
```

等价子网掩码：

```text
255.255.255.0
```

## 子网划分

假设存在：

```text
192.168.1.0/24
```

现在希望划分成两个子网：

```text
192.168.1.0/25
192.168.1.128/25
```

可以理解为：

```text
192.168.1.0/24
       │
       ├─────────────┐
       ↓             ↓
192.168.1.0/25   192.168.1.128/25
```

子网划分可以用于：

```text
地址规划
网络隔离
缩小广播域
组织不同网络
```

### 子网大小

对于 IPv4：

```text
/24
→ 32 - 24 = 8 bit 主机部分

2^8 = 256
```

传统 IPv4 子网中通常需要保留：

```text
网络地址
广播地址
```

因此普通主机通常可使用：

```text
256 - 2 = 254
```

个地址。

例如：

```text
192.168.1.100
```

属于私有地址。

```text
默认网关
```

例如：

```text

8.8.8.8
```


不属于：

```text

```

所以：

```text
本机
 ↓
默认网关
 ↓
其他网络
```

## 路由

路由解决的问题是：

> IP 数据包下一步应该发送到哪里？

可以把路由理解成：

```text
目标网络
    ↓
下一跳
    ↓
输出接口
```

例如：

```text
目标：
10.10.0.0/16

下一跳：
192.168.1.254
```

含义：

```text
访问 10.10.0.0/16
        ↓
交给 192.168.1.254
```

### 默认路由

默认路由：

```text
0.0.0.0/0
```

表示：

```text
没有更具体匹配项时
使用这条路由
```

---

## 最长前缀匹配

假设存在：

```text
10.0.0.0/8
10.10.0.0/16
10.10.1.0/24
0.0.0.0/0
```

访问：

```text
10.10.1.50
```

它同时匹配：

```text
10.0.0.0/8
10.10.0.0/16
10.10.1.0/24
```

最终使用：

```text
10.10.1.0/24
```

因为它的网络前缀最长。

这就是：

```text
Longest Prefix Match
→ 最长前缀匹配
```

它是理解 IP 路由选择的重要基础。

## 路由器

路由器主要根据：

```text
目标 IP
+
路由表
```

进行三层转发。

例如：

```text
网络 A
192.168.1.0/24
        ↓
     路由器
        ↓
网络 B
192.168.2.0/24
```

路由器收到 IP 数据包后，会：

```text
读取目标 IP
    ↓
查询路由表
    ↓
选择下一跳
    ↓
通过对应接口发送
```

### 每经过一个路由器会发生什么？

一个重要的理解：

```text
IP 数据包
```

在不同网络之间转发时，其：

```text
链路层帧
```

会不断变化。

例如：

```text
Host A
 ↓
Frame A→Router1
 ↓
Router1
 ↓
Frame Router1→Router2
 ↓
Router2
 ↓
Frame Router2→Host B
```

但 IP 层仍然保持：

```text
源 IP
+
目标 IP
```

的端到端语义。

因此：

```text
MAC
→ 一跳一跳变化

IP
→ 负责端到端网络寻址
```

## TTL

IPv4 首部包含：

```text
TTL
Time To Live
```

它用于限制数据包能够经过的路由跳数。

通常每经过一个路由器：

```text
TTL
↓
减 1
```

如果变成：

```text
0
```

数据包就会被丢弃，并通常产生：

```text
ICMP Time Exceeded
```

这也是路径探测机制能够发现中间路由器的重要基础。

---

## MTU

MTU（Maximum Transmission Unit）表示：

> 一条网络链路能够承载的最大 IP 数据包大小。

典型 Ethernet MTU：

```text
1500 bytes
```

如果数据包超过下一条链路的 MTU，就可能需要：

```text
分片
```

或者：

```text
调整发送大小
```

IPv4 支持分片。

而 IPv6 的设计不同：

```text
IPv4
→ 路由器可以参与分片

IPv6
→ 中间路由器不负责分片
→ 由源节点处理
```

RFC 8200 对 IPv6 分片机制进行了规定。([RFC 8200](https://www.rfc-editor.org/rfc/rfc8200))

MTU 问题常见于：

```text
VPN
隧道
虚拟化
复杂云网络
```

## ICMP

ICMP 用于传递 IP 层相关的控制和错误信息。

典型消息包括：

```text
Echo Request / Reply
Destination Unreachable
Time Exceeded
Packet Too Big
```

ICMP 并不是一个“可靠传输协议”。

它主要承担：

```text
错误报告
网络诊断
控制信息
```

RFC 792 定义了 IPv4 中的 ICMP。([RFC 792](https://www.rfc-editor.org/rfc/rfc792))

因此核心概念是：

```text
TCP
UDP
Port
Socket
```

可以把网络通信进一步理解为：

```text
IP
→ 找主机

Port
→ 找传输层端点

Application Protocol
→ 定义业务数据
```

例如：

```text
192.168.1.100:443
```

其中：

```text
192.168.1.100
```

应用程序通常通过 Socket 使用网络。

可以粗略理解为：

```text
Socket

传输层端点
```

对于 TCP 连接，可以用：

```text
源 IP
+
源端口
```

## TCP

TCP（Transmission Control Protocol）提供：

```text
面向连接
可靠传输
有序字节流
流量控制
拥塞控制
```

当前 TCP 核心规范是 RFC 9293。([RFC 9293](https://www.rfc-editor.org/rfc/rfc9293))

---

## TCP 是字节流

这是 TCP 非常重要的特性：

> TCP 是字节流协议，而不是消息协议。

例如应用程序发送：

```text
send("hello")
send("world")
```

接收方不能假设：

```text
第一次读取
→ hello

第二次读取
→ world
```

可能出现：

```text
helloworld
```

也可能：

```text
hel
lowor
ld
```

TCP 保证的是：

```text
字节顺序正确
```

而不是：

```text
应用层消息边界
```

因此应用协议需要自己设计：

```text
长度字段
分隔符
固定长度
```

等消息边界机制。

---

## TCP 三次握手

TCP 建立连接：

```text
客户端                         服务端

   SYN
────────────────────────→

                SYN + ACK
←────────────────────────

   ACK
────────────────────────→
```

可以理解为：

```text
SYN
→ 请求建立连接

SYN + ACK
→ 同意建立，并确认客户端

ACK
→ 确认服务器
```

建立完成之后：

```text
客户端
   ↕
 TCP
   ↕
服务器
```

TCP 建连过程与初始序列号同步有关，因此并不是简单的“三次打招呼”。

---

## TCP 序号与确认

TCP 使用：

```text
Sequence Number
Acknowledgment Number
```

跟踪字节流。

例如发送：

```text
SEQ = 1000
Length = 1000
```

表示发送：

```text
1000 ~ 1999
```

如果接收方成功收到，可以回复：

```text
ACK = 2000
```

表示：

```text
已经收到 2000 之前的数据
下一步希望收到 2000
```

因此：

```text
ACK = 下一步期望的序号
```

比简单理解成：

```text
ACK = “我收到了这个数据包”
```

更加准确。

## TCP 重传

网络中可能发生：

```text
丢包
乱序
重复
```

例如：

```text
Segment 1
    ↓
Segment 2
    X
  丢失
    ↓
Segment 3
```

TCP 可以通过：

```text
确认
重复 ACK
超时
快速重传
```

等机制发现数据缺失并重新发送。

因此：

```text
IP
→ 尽力传输

TCP
→ 在 IP 之上提供可靠的字节流
```

## TCP 流量控制与拥塞控制

这两个概念经常混淆。

### 流量控制

解决：

```text
发送方
vs
接收方
```

例如接收方处理不过来：

```text
接收窗口变小
↓
发送方降低发送量
```

核心目标：

```text
防止接收方被发送方压垮
```

### 拥塞控制

解决：

```text
发送方
vs
整个网络
```

例如：

```text
大量数据
↓
路由器队列增加
↓
延迟增加
↓
丢包
```

TCP 会根据网络状态调整发送速率。

经典机制包括：

```text
慢启动
拥塞避免
快速重传
快速恢复
```

RFC 5681 对经典 TCP 拥塞控制进行了规范化描述。([RFC 5681](https://www.rfc-editor.org/rfc/rfc5681))

因此：

```text
流量控制
→ 防止接收方过载

拥塞控制
→ 防止网络过载
```

## TCP 四次挥手

TCP 是全双工连接，因此关闭连接时双方需要分别关闭自己的发送方向。

典型过程：

```text
客户端                         服务端

   FIN
────────────────────────→

              ACK
←────────────────────────

              FIN
←────────────────────────

   ACK
────────────────────────→
```

因此通常表现为：

```text
四次挥手
```

它与：

```text

```

等 TCP 机制有关。

因此：

```text

≠
连接异常
```

是否需要处理，要结合：

等实际情况判断。

## UDP

UDP（User Datagram Protocol）提供：

```text

```

UDP 本身不提供 TCP 那样的：

```text

```

RFC 768 定义了 UDP。([RFC 768](https://www.rfc-editor.org/rfc/rfc768))

常见使用场景：

```text

实时音视频
直播
游戏
```

需要注意：

> UDP 本身不提供可靠传输，不等于使用 UDP 的应用一定不可靠。

应用程序可以在 UDP 之上自行实现：

```text
序号
确认
重传
拥塞控制
```

## TCP 与 UDP

| 特性    | TCP  | UDP   |
| ----- | ---- | ----- |
| 连接    | 面向连接 | 无连接   |
| 数据模型  | 字节流  | 数据报   |
| 可靠传输  | 有    | 无     |
| 重传    | 有    | 无     |
| 按序交付  | 有    | 不保证   |
| 流量控制  | 有    | 无     |
| 拥塞控制  | 有    | 协议本身无 |
| 协议复杂度 | 较高   | 较低    |

不要简单理解成：

```text
TCP = 慢
UDP = 快
```

真正的区别是：

```text
TCP
→ 协议本身提供丰富的传输控制机制

UDP
→ 提供更简单的数据报传输能力
```

## NAT

NAT（Network Address Translation）用于对网络地址进行转换。

## RTT

RTT（Round Trip Time）表示：

```text

 ↓

 ↓

```

整个往返所需的时间。

可以理解为：

```text

```

网络延迟受到很多因素影响：

```text
物理距离
链路质量
路由路径
网络拥塞

```

因此两台主机之间的 RTT 不仅取决于带宽。

## 带宽、吞吐量、延迟、RTT

这几个概念也很容易混淆：

| 概念  | 含义             |
| --- | -------------- |
| 带宽  | 链路理论上的数据传输能力   |
| 吞吐量 | 实际一段时间内传输了多少数据 |
| 延迟  | 数据从一端到另一端所需时间  |
| RTT | 数据往返一次所需时间     |
| 丢包率 | 数据包丢失比例        |

例如：

```text
高带宽
≠
低延迟
```

一条链路可能：

```text
带宽很高
但 RTT 很大
```

典型于地理距离较远的通信场景。
